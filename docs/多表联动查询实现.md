# 多表联动检索：实现说明

日期：2026-11-15（路径已于 2026-11-18 更新为 `web/` 版本） · 对应需求：「前端多表联动数据查询，支持组装 SQL 和存储过程传参」

> 前端已从 Vite 版（`frontend/`）切换到免构建的 `web/` 版本，本文中出现的 `frontend/src/views/BookListView.vue`、`src/api/catalog.js` 均为旧路径，对应现文件为 `web/src/components/LibraryView.js` 与 `web/src/services/api.js`。逻辑未变。

## 一、它落在哪一层

| 层 | 做什么 | 文件 |
|---|---|---|
| 前端 | 只负责收集条件、发请求、渲染；**不拼任何 SQL** | `web/src/components/LibraryView.js`、`web/src/services/api.js` |
| 接口层 | 收参数、包响应，不出现 SQL 字符串 | `services/catalog-service/.../web/BookController.java` |
| 编排层 | 参数归一化、选择通道、决定 total 怎么取 | `.../query/BookSearchService.java`、`BookQuery.java` |
| 组装层 | 动态 SQL（MyBatis `<if>`）与存储过程调用 | `resources/mapper/BookQueryMapper.xml` |
| 数据层 | 存储过程 + 索引 | `database/catalog/020_book_search.sql`、`010_search_index.sql` |

一次请求真正跨了 5 张表：`book`、`category`、`author`、`book_author`、`media`。

## 二、两条通道，同一份结果

```
GET /api/catalog/books?keyword=红楼&categoryId=1&status=ON_SHELF&sortBy=updatedAt&sortOrder=desc&page=1&size=10
        │
        ├── catalog.search.mode=sql  →  BookQueryMapper.searchBySql   （MyBatis 组装）
        └── catalog.search.mode=proc →  BookQueryMapper.searchByProc  （CALL catalog.fn_search_books）
```

切换只改 `application.yml` 一行（或环境变量 `SEARCH_MODE`），前端零改动。存储过程抛错时自动回退到动态 SQL，检索不会整体挂掉。

## 三、三个必须做对的地方

### 1. 排序字段只能来自枚举

`ORDER BY` 的列名不能参数绑定，只能拼字符串。所以：

- `BookSortField` 枚举是**唯一**的列名来源，`BookQuery.of()` 里完成 `sortBy → 列名` 转换；
- Mapper 里写 `${q.sortColumn}`，取的是枚举产出的常量，不是请求值；
- 未知字段直接抛 `INVALID_SORT_FIELD`（400），**不静默回退**——回退会让前端以为排序生效了；
- 存储过程内部再做一次同样的白名单校验，双保险。

### 2. 值一律预编译

```xml
AND b.title ILIKE '%' || #{q.keyword} || '%'
```

`#{}` → 预编译占位符；`${}` 只出现在排序那一处。存储过程调用同理，`#{...}` 全部显式标注 `jdbcType`——否则参数为 `null` 时 openGauss/PG 驱动会报 `could not determine data type of parameter`。

### 3. total 尽量少查一次

- 动态 SQL 通道：本页没填满就说明是末页，`total = offset + 实际条数`，免掉一次 count；只有填满一页才真 count。
- 存储过程通道：`count(*) OVER()` 随结果一起返回，一次往返且与数据同一快照。

## 四、验证结果（本地 PostgreSQL 16 WASM 实测）

**存储过程行为，11 个用例全部符合预期：**

| # | 场景 | 结果 |
|---|---|---|
| 1 | 无条件 + 默认排序 | 7 条，total=7 |
| 2 | 分类=计算机 | 2 条 |
| 3 | 关键词命中书名 | 1 条 |
| 4 | 关键词命中出版社 | 2 条 |
| 5 | 关键词命中作者（EXISTS 子查询） | 1 条 |
| 6 | 只看在架 | 6 条 |
| 7 | 组合条件 + 第 2 页 size=3 | 3 条，total=6 |
| 8 | 非法排序字段 `password` | 抛 `INVALID_SORT_FIELD` |
| 9 | 非法状态 `DROP` | 抛 `INVALID_ARGUMENT` |
| 10 | size=1000 超上限 | 自动夹到 100 |
| 11 | 页码越界 page=99 | 返回 0 行，**total 丢失**（见下） |

**双通道一致性，7 组参数逐组比对 book_id 序列：7/7 完全一致。**

## 五、三个已知取舍

### 1. 页码越界时 total 拿不到（已补）

`count(*) OVER()` 依附在结果行上，结果为空就没有行可挂，total 只能是 0。而契约里 `totalPages` 依赖 total，前端会显示「共 0 条」。

处理：`BookSearchService.searchByProc()` 里判断——第 1 页为空视为真的没数据（total=0）；第 N 页（N>1）为空则补一次 `fn_count_books`。这是**已知缺陷 + 明确补救**，不是遗漏。

### 2. 前端原来的两个排序项后端不支持（已改）

`BookListView.vue` 原本有「借阅最多 `borrowCount`」和「价格 `price`」。这两列在 `catalog` schema 里不存在（借阅次数在 D 的 `report.loan_fact`，价格明确不加），契约白名单也只有 `updatedAt / title / publishYear`。接真实后端就会 400。

已改为：最近更新 / 出版年份 / 书名。要恢复「借阅最多」，得等 D 提供 `/api/reports/hot` 后再单独接。

### 3. 分类只支持一级

存储过程用 `b.category_id = ?` 精确匹配。前端 mock 里支持 `parentId` 子树递归，但契约明确「课程只演示一级分类，不引入树形」。**如果要支持子树**，把条件换成：

```sql
AND ($1 IS NULL OR b.category_id IN (
    WITH RECURSIVE sub AS (
        SELECT category_id FROM catalog.category WHERE category_id = $1
        UNION ALL
        SELECT c2.category_id FROM catalog.category c2 JOIN sub ON c2.parent_id = sub.category_id
    ) SELECT category_id FROM sub))
```

前提是 D 给 `category` 加 `parent_id` 列——这是改库，需要单独提。

## 八、新增：全部图书页的多条件联动查询（2026-11-19）

「全部图书」页从「前端内存过滤」改成了「后端多条件检索」，一次请求真正落在数据库侧。

### 接口

```
GET /api/catalog/books/search
    ?title=&author=&publisher=&isbn=&categoryId=&yearFrom=&yearTo=
    &status=ON_SHELF|OFF_SHELF|ALL&sortBy=updatedAt|title|publishYear|bookId
    &sortOrder=asc|desc&page=1&size=12
```

### 代码落点

| 层 | 文件 | 职责 |
|---|---|---|
| 前端页面 | `web/src/components/LibraryView.js` | 多条件表单、分类芯片、分页；**不拼 SQL、不做本地过滤** |
| 前端服务 | `web/src/services/api.js` 的 `searchBooks()` | 参数序列化 + 结果映射成 BookCard 需要的形状 |
| 控制器 | `.../web/BookController.java` 的 `GET /books/search` | 收参数、包响应 |
| 编排 | `.../query/BookMultiQuery.java` | 参数归一化：去空白、长度≤100、年份 1000–2100、`from ≤ to`、状态白名单、排序白名单、分页夹取 |
| 组装 | `.../resources/mapper/BookQueryMapper.xml` 的 `multiWhere` / `searchMulti` / `countMulti` | 一个条件一个 `<if>`，值全部 `#{}` |
| 结果 | `.../query/MultiSearchResult.java` | 分页 + `joinTables` + `appliedConditions` |

### 与原有单关键词检索的关系

- `/books` 保持不动：首页预加载、控制台书目管理、导出都还在用它；
- `/books/search` 只服务「全部图书」页的多条件表单；
- **只走动态 SQL 通道**，不上存储过程：多条件要分别按标题 / 作者 / 出版社 / 年份过滤，
  而 `catalog.fn_search_books` 的签名是「单关键词 + 分类 + 状态」，硬塞要么改已验收的过程签名，
  要么在 PL/pgSQL 里再拼一遍动态 SQL（等于把注入风险搬进数据库）。取舍写在
  `BookSearchService.searchMulti` 的注释里。

### 三个容易踩的点

1. **作者过滤用 EXISTS，不用 JOIN**：一本书有多个作者时，JOIN 会把行数放大，
   分页的 total 与页码立刻对不上；EXISTS 只判断"有没有"，不复制行。
2. **status 不传 = 不限**：`/books` 的默认是只看在架，两者语义不同。前端默认传 `ON_SHELF`，
   这样"默认视图"仍是 17 种；用户选「全部」才会看到已下架的《数据库》。
3. **年份区间是闭区间**：`publish_year >= yearFrom AND <= yearTo`，两个边界都可只填一个。

## 九、「可借 / 馆藏」口径与副本补登（2026-11-19 补）

### 口径

```
馆藏 = catalog.book.total_copies（>0 时）    兜底：loan.book_copy 实际册数
可借 = max(0, 馆藏 - 已借出)
已借出 = loan.book_copy 中 status ∈ {BORROWED, OVERDUE} 的册数
```

两个数字同源、永远自洽：馆藏 5、借出 1 → 显示 `4 / 5`。

### 上一版为什么全显示 0

`preload()` 只请求一次 `GET /api/copies?after=0`，而该接口 **每页最多 100 条**
（`limit 100` + copy_id 游标）。副本表有 1000+ 行时，前 100 条之后的书全被判成
「0 册副本 → 可借 0」。改为按游标翻完全部页（`fetchAllCopies()`），并对 401 之外的
偶发失败重试两次。

### 副本补登为什么必须批量

原先前端一册一个 `POST /api/copies`，导入 200 行 × 5 册 = 1000 次请求，浏览器在
中途被中断后，`catalog.book.total_copies` 已是 5 而 `loan.book_copy` 只有 0–4 册，
表里就会出现「馆藏 5、实际 0」的书。

新增 `POST /api/copies/batch`（loan-service）：

```json
请求 { "bookId": 143, "title": "经济学原理", "isbn": "978-7-...", "count": 5 }
响应 { "bookId": 143, "before": 0, "created": 5, "total": 5 }
```

- 单事务内完成 `book_snapshot` upsert + 补足差额的 `book_copy` 插入；
- **幂等**：已有 5 册时 `created = 0`，不会重复建；
- 条码 `B{bookId}-{序号}`，序号从该书的现有最大序号往后排，撞号自动跳过；
- 已有副本只增不减，降馆藏数不会删副本（删副本会影响借阅记录）。
